## Findings

### B2-01 — Cache PER corrompu, sans fraîcheur, alimentant des décisions d'achat/vente — **P1**

- **Fichiers** : `src/collecte/fundamentals.py:44-86` · `data/per_cache.json` · `src/analyse/screener.py:25-82` · consommateurs : `src/portfolio.py:500-503, 724-734` · `src/strategie/orders.py:47`
- **Description** : `get_per_brvm()` scrape `https://www.brvm.org/fr/<code>` avec une regex très spécifique (`PER:&nbsp;</div><div class="field-items">…`). Si le statut n'est pas 200, si la regex ne matche pas, ou si le réseau tombe, la fonction **retourne la dernière valeur du cache `data/per_cache.json` — indéfiniment**. Or :
  - `per_cache.json` ne stocke **aucune date** (`{code: per}`, plat) — l'âge d'un PER est **indéterminable** ;
  - le fichier n'a **pas été écrit depuis le 09/09** (mtime `sept. 9 09:13`, 33 jours) alors que le cache secondaire `fundamentals_cache.json` a été rafraîchi le 08/10 → **le scraping PER est en panne silencieuse depuis ~1 mois** et la production tourne sur des PER du 09/09 (ou plus vieux) ;
  - les valeurs en cache sont **implausibles pour au moins 11 titres** : `UNLC 688,39`, `BNBC 578,76`, `BOAN 254,11`, `SDSC 211,86`, `SIVC 96,7`, `SAFC 72,73`, `FTSC 59,63` (PER > 50 = `PER_ABSURD`, absurdes pour des banques BRVM qui traitent à PER 5-20) et **`STAC 0,0`, `SICC 0,0`, `SCRC 0,0`, `UNXC 0,0`** (PER nul = champ mal scrapé, ex. un prix ou un « n/a » interprété) ;
  - aucune validation de plausibilité n'existe à la couche collecte (`fundamentals.py`) — les seuls filtres (`PER_ABSURD = 50`, `PER_MAX = 14`, `PER_EXPLODE = 40`) sont en aval, dans les consommateurs.
- **Scénario d'impact** : `src/portfolio.py:500-503` : `if not pos.closed and current_per is not None and current_per > PER_EXPLODE (40,0)` → alerte **« 🔴 VENDS TOUT — PER 96,7 > 40 »**. `current_per` vient de `get_per_brvm()` (portfolio.py:724-734), donc du cache sans date. **SIVC — qui est dans la watchlist de `config.yaml` — a un PER caché de 96,7 > 40** : si LEO détient SIVC (ou l'achète via la watchlist) et que le scraping brvm.org est en panne (c'est le cas depuis le 09/09), une alerte « VENDS TOUT » **fausse** part sur Telegram. À l'inverse, un PER caché de 0,0 fait passer un titre dans les filtres « value » (`screener.py:103` `per <= PER_MAX`) et en **tête du tri par PER** (`screener.py:113` `out.sort(key=lambda r: r["per"])` — les PER 0,0 passent le filtre `per > 0`? non : `if not per or per <= 0 … continue` les exclut — mais `orders.py:47` et `portfolio.py:683` gèrent aussi `per <= 0` ; le risque 0,0 est donc filtré en aval, le risque « PER absurde > 40 » ne l'est pas partout). Le conseil de renforcement (`orders.py`) calcule aussi un payout à partir de ce PER.
- **Preuve citée** : `fundamentals.py:81-86` : `cache = _load_per_cache(); if per is not None: … return per; return cache.get(code)` ; `per_cache.json` : `"UNLC": 688.39`, `"BNBC": 578.76`, `"BOAN": 254.11`, `"SDSC": 211.86`, `"SIVC": 96.7`, `"SAFC": 72.73`, `"FTSC": 59.63`, `"STAC": 0.0`, `"SICC": 0.0`, `"SCRC": 0.0`, `"UNXC": 0.0` ; mtime du fichier `sept. 9 09:13` vs `fundamentals_cache.json` `oct. 8 09:33` ; `portfolio.py:500-503` (VENDS TOUT si PER > 40).
- **Recommandation** : (1) stocker `{per, scraped_at, source}` par titre et refuser un PER plus vieux qu'un seuil (ex. 7 jours) — le servir alors comme `None`, pas comme valeur ; (2) valider la plausibilité à l'écriture (0 < PER < 100, sinon ne pas mettre en cache) ; (3) investiguer la panne du scraping brvm.org (la regex ne matche probablement plus la page) — c'est la cause racine ; (4) purger les valeurs absurdes du cache.

### B2-02 — Vérification TLS désactivée sur toutes les sources de données externes — **P2**

- **Fichiers** : `src/collecte/bsapi.py:22,37` · `src/collecte/live.py:22,52` · `src/collecte/dividend_history.py:20,32` · `src/analyse/boc.py:25,79,132` · `src/analyse/news.py:22,83` · `scripts/madis_feed.py:21,52` · `scripts/detachements.py:14,23` · `scripts/mesurer_couverture_fondamentaux.py:30,40` · `scripts/parse_avis_ocr.py:47,67` · `scripts/sika_api_probe*.py` (5 scripts) · `scripts/challenge_strategie.py:37,157`
- **Description** : `verify=False` (ou `session.verify = False`) sur **chaque source de données externe du projet**, accompagné de `urllib3.disable_warnings(...)` exécuté **à l'import du module** (effet de bord global qui désactive les avertissements TLS pour tout le processus, y compris les autres bibliothèques). La justification avancée dans `bsapi.py:9` est « le certificat SSL du serveur est invalide ». Conséquence : n'importe quel MITM sur le réseau (Wi-Fi d'hôtel, FAI, machine compromise) peut modifier **les kotations, l'historique OHLCV, les dividendes, les annonces officielles** — c'est-à-dire les données qui déclenchent les alertes d'achat/vente et les décisions de LEO. C'est la chaîne d'approvisionnement de données du système entier, en clair.
- **Preuve citée** : `bsapi.py:37` `self.session.verify = False` (toutes les requêtes BSTrade : snapshot, horaires, historique) ; `live.py:52` `requests.get(URL, …, verify=False)` (brvm.org, cours temps réel) ; `dividend_history.py:32` `verify=False` (stockanalysis.com — alimente les filtres d'entrée noyau) ; `news.py:83` `verify=False` (annonces officielles BRVM) ; `boc.py:79,132` `verify=False` (BOC + Sika) ; `madis_feed.py:52` `verify=False`.
- **Scénario** : un MITM renvoie un faux snapshot BSTrade avec un cours PALC à −15 % → alerte « DÉCISION — CONSERVE/renforce » ou « stop » fabriquée ; un faux dividende BNBC dans stockanalysis.com → filtre noyau faussé.
- **Recommandation** : (1) ne jamais désactiver la vérification TLS pour des données qui pilotent des décisions financières ; (2) si le certificat BSTrade est réellement invalide, le signaler à Bridge Securities et utiliser un *pinning* (empreinte de certificat connue) plutôt que `verify=False` ; (3) centraliser le client HTTP (`infrastructure/http.py` prévu par le plan) avec `verify=True` par défaut et un seul point de dérogation documenté ; (4) retirer les `disable_warnings()` des imports de modules.

### B2-03 — Deux caches de fondamentaux pour le même fait, divergents, deux politiques de fraîcheur — **P2**

- **Fichiers** : `data/per_cache.json` (sans date) vs `data/fundamentals_cache.json` (avec `scraped_at`, 24 h) · `src/collecte/fundamentals.py:44-58` · `src/analyse/screener.py:25-82`
- **Description** : le PER d'un titre existe en **deux endroits** : `per_cache.json` (écrit par `get_per_brvm`, **plat, sans date, sans fraîcheur**) et `fundamentals_cache.json` (écrit par `screener.scrape_all_fundamentals`, avec `scraped_at` et péremption 24 h). Les deux divergent déjà : PALC **7,73 vs 8,35**, SGBC **12,03 vs 11,97**, BOAS **13,56 vs 13,47**, SOGC **13,83 vs 13,65**, SLBC **13,34 vs 13,45**. Pire : `screener.py:73` écrit `{"per": get_per_brvm(code), …, "scraped_at": datetime.now()}` — quand le scraping échoue, `get_per_brvm` retourne la valeur **du cache sans date**, et screener la tamponne `scraped_at = maintenant` : **l'indicateur de fraîcheur de 24 h est faux** — il date l'écriture du cache, pas la donnée. La « fraîcheur » affichée est un mensonge statistique.
- **Preuve citée** : `screener.py:52-59` (`_cache_fresh` lit `scraped_at`) + `screener.py:73` (stocke `get_per_brvm(code)` + `scraped_at: now`) ; `fundamentals.py:81-86` (retour du cache sans date) ; valeurs divergentes citées ci-dessus (diff des deux fichiers lus le 12/10).
- **Scénario** : un consommateur lit `fundamentals_cache.json` (cru « frais »), un autre `per_cache.json` (via `get_per_brvm` direct : `orders.py:47`, `portfolio.py:724`) — deux PER différents pour le même titre le même jour, deux décisions différentes selon le chemin d'appel.
- **Recommandation** : une seule source de vérité pour le PER (un cache, un schéma `{per, dps, scraped_at, source}`), la fraîcheur portée par la donnée elle-même, et `get_per_brvm` ne servant un cache périmé que comme `None` + log.

### B2-04 — Cron « check quotidien » : faux-vert par construction (wrapper + heartbeat + marqueurs de panne) — **P2**

- **Fichiers** : `scripts/daily_check.py:27-36` · `scripts/report_check.py:26-35` · `src/main.py:1268-1288` · `src/analyse/news.py:82-86` · wrappers `%LOCALAPPDATA%/hermes/scripts/bridgebank_daily.py`, `bridgebank_report.py`
- **Description** : la chaîne de production du check quotidien est **verte même quand tout échoue** :
  1. `daily_check.py:31-33` : `except Exception: traceback.print_exc()` dans `logs/daily.log` (gitignored, jamais relu) puis **sortie en code 0** ;
  2. le wrapper Hermes `bridgebank_daily.py` fait `subprocess.run([sys.executable, SCRIPT], check=True)` — sa détection d'erreur (`check=True`) est **rendue inopérante** par le point 1 : le check plante → daily_check sort 0 → le wrapper sort 0 → le cron Hermes voit « ok » ;
  3. `cmd_daily` (`main.py:1273-1278`) isole chaque étape (`except Exception: print("⚠ échec …")`) — **puis envoie quand même le heartbeat** avec « ✅ Check quotidien Bridge Bank » (`main.py:1299-1300`) et le statut de l'étape en « 🔔 événement » même quand elle a planté ;
  4. les marqueurs « rien à signaler » sont aussi produits par des **chemins de panne silencieuse** : `news.py:85-86` `except requests.RequestException: continue` → `fetch_announcements()` retourne `[]` → `cmd_news` imprime « Aucune nouvelle annonce sur le noyau. » → heartbeat « ✅ Annonces BRVM : rien à signaler » **pendant une panne réseau totale**. Idem pour `cmd_boc` (« BOC indisponible » ne contient pas le marqueur, lui, mais `cmd_fund`/`cmd_watchlist` peuvent avoir leurs propres replis).
- **Preuve citée** : `daily_check.py:31-35` (`except Exception: … finally: sys.stdout, sys.stderr = _stdout, _stderr` — aucune propagation, exit 0) ; `bridgebank_daily.py` (`subprocess.run(..., check=True)`) ; `main.py:1275-1276` (`except Exception as e: print(f"⚠ échec : {e}")`) + `main.py:1287-1288` (envoi inconditionnel du heartbeat) ; `news.py:85-86` (`continue  # source indisponible = couverture inconnue`).
- **Scénario** : BSTrade ou brvm.org est down un matin de séance → le check « réussit », LEO reçoit « ✅ Check quotidien … tout va bien », **aucune alerte**, aucun signal nulle part (les logs sont ignorés par git et jamais consultés). Le système de surveillance est précisément celui qui doit détecter les pannes — il est le dernier à les voir.
- **Recommandation** : (1) `daily_check.py` doit propager l'échec (exit non nul) — le wrapper `check=True` est là pour ça ; (2) le heartbeat ne doit pas porter « ✅ » quand une étape a levé — distinguer « ✅ rien à signaler » (marqueur présent) de « ⚠ étape en échec » (exception) et « ❌ source indisponible » (fetch vide à cause d'une erreur réseau, pas d'une absence d'annonce) ; (3) `fetch_announcements` doit distinguer « 0 annonce » de « site injoignable ».
